# Kubernetes

Two things are deployed here, and they are deliberately separate: the builds that
produce images, and the web page that shows you what the builds are doing. The
builds are a Helm chart. The page is a generated manifest. Either can be deployed
without the other — the chart alone gives you scheduled builds with no UI, and the
page alone gives you a dashboard with nothing to display.

## What is here

```text
kubernetes/
├── charts/packer-imaging/    the build CronJobs, and the namespaces they run in
├── runner/Dockerfile         the image those CronJobs run
└── workloads/
    └── web-frontend.yaml     the web page, generated - do not edit by hand
```

`charts/packer-imaging/` is the only place a build project is defined. It creates
one CronJob per entry in `.values.projects`, so adding a distribution is a change
to `values.yaml` and nothing else. `charts/packer-imaging/README.md` is the value
reference.

`workloads/web-frontend.yaml` is generated by `web/tools/gen-manifest.py` from the
files in `web/`. Editing it directly means the next regeneration reverts the edit,
and `web/tests/test_manifest.py` fails until it is regenerated. See
[Web front end](../docs/operations/web-front-end.md).

## Install order

The chart creates both namespaces. The manifest is applied into one of them, so
it comes second.

```shell
helm upgrade --install packer-imaging kubernetes/charts/packer-imaging \
  --namespace packer-imaging --create-namespace

kubectl apply -f kubernetes/workloads/web-frontend.yaml
```

Two Secrets must exist in the builds namespace before a run can start, and
neither is created by the chart because both carry credentials. The chart's
`NOTES.txt` prints the exact `kubectl create secret` commands for your values on
install; [Secrets](../docs/operations/secrets.md) explains what goes in them.

## The naming contract

The page does not keep its own list of projects. It reads CronJobs and works out
what it is looking at from two things the chart sets:

| The page reads | From | Where it is set |
| :------------- | :--- | :-------------- |
| the project name | the `packer.io/project` label | `templates/cronjobs.yaml` |
| the project from a run | the `jobPrefix` on the CronJob name | `values.yaml` |
| the build directory | the `PACKER_PROJECT` env var | `templates/cronjobs.yaml` |
| which Secrets are needed | the pod's volume and `envFrom` mounts | `templates/cronjobs.yaml` |

`jobPrefix` defaults to `aria-build-` and so does `PROJECT_PREFIX` in
`web/runs.py`. Those two constants are the same contract written twice. Change
one without the other and every run is shown as an orphan: the page still works,
and every build becomes unattributed. Change them together, or leave them alone.

## Validating

There is no cluster in CI, so what is checked is the rendered output, not an
install.

```shell
helm lint kubernetes/charts/packer-imaging
helm template packer-imaging kubernetes/charts/packer-imaging
```

`helm template` is also the way to see what a values change actually does. One
CronJob per project directory under `builds/` is expected; if the two counts
disagree, `values.yaml` and the filesystem have drifted apart.
